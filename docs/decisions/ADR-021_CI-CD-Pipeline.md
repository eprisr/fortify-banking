# ADR-021: CI/CD, a First Pipeline on GitHub Actions

**Date:** 2026-10-31  
**Status:** Accepted  
**Author:** Epris R

---

## Context

Fortify has no automated checks. There's no `.github/` directory, and everything that guards the code, linting, the Jest suite, type checking and the Playwright tests, only runs when I remember to run it. Vercel deploys from Git, so a push to `main` goes live whether or not any of that has passed.

That was fine while I was the only one touching a small app. It isn't fine for what's next. The desktop work (ADR-020) touches every layout, and Stage 1.5 adds a Postgres ledger, migrations and a queue. I want a safety net in place before either of those starts, not after. I'm also new to CI/CD, so this ADR is as much about picking a small first step I can understand as it is about picking tools.

### What setting this up turned up

Before writing the pipeline I ran each check on a clean clone. A few things surfaced.

- **Lint is broken.** `npm run lint` calls `next lint`, which Next 16 no longer has. It fails with "Invalid project directory ... /lint". The fix is to call `eslint` directly.
- **There's no type check script.** Running `tsc --noEmit` gives five errors. Two are real, in the reset-password and verify-email tests, where the page props are missing `params`. The other three are missing types for images and SVGs, because `next-env.d.ts` is generated by Next and gitignored. A clean checkout doesn't have it until a build runs.
- **Four Jest suites fail,** 20 tests out of 440. They are plaidlink, navbar, `user.actions.transfer` and `user.actions.demo`. That's not the list I recorded in ADR-014, where two of the four were different, so the picture has moved. The navbar failures include what looks like a real bug, not a stale test. `Navbar` calls `obscureEmail(user!.email)` unconditionally, and the transaction history page renders `<Navbar type="sub" />` with no user, so that page appears to crash on render.
- **Jest is slow with coverage on.** `collectCoverage` is set to true in the Jest config. On the clean clone the full run took many minutes and didn't finish when coverage was on, and finished in a couple of minutes with it off.

---

## Decision

Use **GitHub Actions** with one workflow that runs on every pull request and on every push to `main`. It runs these steps in order.

1. Install with `npm ci`.
2. Lint with `eslint .`.
3. Build with `next build`, which also generates the missing type files.
4. Type check with `tsc --noEmit`.
5. Run Jest with coverage turned off, `jest --coverage=false`.

**Nothing in this pipeline needs a secret.** The Jest suite runs on MSW mocks and a committed `.env.test`, so it's safe to run anywhere.

**CI blocks deploys.** I'll turn on branch protection for `main` and require these checks to pass before a pull request can merge. Vercel's production deploy comes from `main`, so only green code goes live. Preview deploys still happen on every pull request, because I want to look at a change before it merges. The cost is that I stop pushing straight to `main` and work through pull requests. I can keep an admin bypass for emergencies.

**The failing checks get fixed first.** I won't make the pipeline required while it's red. A pipeline that fails on day one trains me to ignore it. The lint script, the two type errors and the four failing Jest suites are fixed before the checks become required.

**End-to-end tests stay out for now.** The Playwright journeys hit the real Plaid sandbox, so they need credentials, and they're slower and flakier than the rest. They get their own workflow later, run manually or nightly, with secrets stored in GitHub Actions secrets. When ADR-016 moves credentials into Doppler, that workflow can pull from Doppler instead.

---

## Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| **GitHub Actions, one workflow** *(chosen)* | Lives next to the code. Free for a public repo. Works directly with branch protection. A good first CI tool to learn. | I have to learn the workflow syntax. |
| **Vercel build only, no separate CI** | Nothing new to set up. | Vercel's build catches build errors only. Tests, lint and types would still be manual. |
| **A third-party CI service** | More features and dashboards. | More setup and another account, with no benefit at this size. |
| **Advisory checks that don't block** | No change to how I push. | A failing check I'm allowed to ignore will get ignored. |

---

## Consequences (Expected)

**Good:**
- A safety net exists before the two largest changes in the project, the desktop refactor and the financial core.
- Bugs like the transaction history crash get caught when they're introduced, not whenever I next look.
- It forces the test suite back to green, which I'd been putting off.

**Bad / Trade-offs:**
- Pull requests add a step to every change, including one-line fixes.
- I have to keep the checks fast and green. A slow or flaky pipeline costs more than it saves.
- The first run will probably need a few rounds of fixes to the workflow itself.

**Risks:**
- `next build` may need environment variables that I haven't thought about, such as public Appwrite and Plaid values or Sentry settings. If so, I'll use placeholder values in CI and note them here.
- Two of the failing Jest suites, `user.actions.transfer` and `user.actions.demo`, may only fail on a clean machine. ADR-014 recorded the transfer tests passing on my machine. If that's the cause, it's the kind of thing CI exists to find, and the fix is in the tests or the environment, not the app.
- Branch protection means a broken pipeline can block me from merging. The admin bypass is the way out, and I should use it rarely.
