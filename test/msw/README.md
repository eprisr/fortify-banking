# MSW test infrastructure

Used by `__tests__/actions/*.test.ts` to mock the real HTTP calls that
`lib/actions/*.ts` make to Plaid and Dwolla, instead of mocking those SDKs
with `jest.mock`. This exercises the actual action code (loops, error
handling, response shaping) against realistic HTTP responses.

- `handlers/plaid.ts`, `handlers/dwolla.ts` — default happy-path handlers,
  one file per provider. Override per test with `server.use(...)`.
- `server.ts` — the `setupServer` instance built from those handlers.
- `setup.ts` — side-effect import that wires `beforeAll`/`afterEach`/
  `afterAll` into Jest. Import it first in any test that needs MSW.

## Why the component tests (`__tests__/home.test.tsx`, `signin.test.tsx`,

etc.) don't use this

Those tests mock whole `@/lib/actions/*` modules with `jest.mock`, not raw
HTTP calls — this app has no client-side `fetch` and no `app/api` routes,
everything goes through `'use server'` actions, so the action module
boundary _is_ the correct seam to stub for a component/page test. Swapping
that for MSW would mean letting real Plaid/Dwolla/Appwrite-calling code run
inside what's meant to be a UI test — see the scope note in each of those
files' header comments.

## Why there's no `handlers/appwrite.ts`

`node-appwrite` (v28) calls `undici.fetch(...)` directly against its own
imported copy of the `undici` package, not `globalThis.fetch`. MSW's node
interceptor (`@mswjs/interceptors`) only patches `globalThis.fetch` and
Node's `http`/`https` modules — it does not patch calls made through a
directly-imported `undici` module, which bypasses Node's `http` module
entirely. This was verified empirically (not just from docs): a probe
script hitting the same MSW server via `fetch(...)` succeeded and via
`undici.fetch(...)` failed with a real (bypassed) network error.

Practical effect: `lib/actions/user.actions.ts` and
`lib/actions/transaction.actions.ts` are almost entirely Appwrite calls and
aren't good MSW targets. `lib/actions/bank.actions.ts` mixes Plaid (axios →
interceptable) with a couple of Appwrite-backed calls it imports from
`user.actions` (`getBanks`, `getBank`) — the tests here `jest.mock` just
those two functions and let the rest of `bank.actions.ts` run for real
against MSW-mocked Plaid responses. `user.actions.ts`'s `createLinkToken` is
pure Plaid with no Appwrite dependency, so it's tested directly the same
way.

If Appwrite coverage via MSW becomes worth the investment later, the fix is
either an `undici`-specific interceptor (`@mswjs/interceptors`'s
`UndiciInterceptor`, if/when stable) or `undici.MockAgent` /
`setGlobalDispatcher` used directly instead of MSW.
